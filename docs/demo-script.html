Name it

ActionWitness. The agent says it did the thing. ActionWitness says what actually happened.

0:26–1:12Beat 1

The layered failure

On screen Arm the cart contract. Drive search_catalog → update_cart → apply_discount from the agent side. Land on the verdict panel.

Same journey, watched. A person and an agent share one workspace, and every tool call the agent makes is recorded through WebMCP.

apply_discount returns success and reports the discounted total. ActionWitness doesn't take its word for it — it reads the cart through a second channel the tool doesn't control.

Expected twenty. Observed twenty-five. Failed — false success or state mismatch. Five other assertions passed. This isn't a broken test. It's a tool that lied, and a harness that noticed.

Pause a full second on the verdict. Expected vs observed, side by side, is the most persuasive frame in the video.

1:12–1:52Beat 2

The agent asks permission

On screen Agent calls proceed_to_checkout. The consent dialog opens and the call visibly waits. Approve once.

Now the consequential one. The agent calls checkout.

It doesn't run. The server issues a confirmation bound to this workspace, this run, these exact arguments — and the agent's call sits there, suspended, until a person decides. An agent cannot create, widen, or approve its own consent.

One approval. Exactly one order. That's the handoff: the agent moves fast, the human owns the consequence.

Scored directly as "quality of the human–agent experience". Let the dialog breathe — show the call pausing, not just the click.

1:52–2:28Beat 3

When the total is right and the run still fails

On screen Administration → failure profile tool_surface_poisoned. Re-run. Show the correct cart total first, then the verdict.

One more, because tools aren't the only thing that can lie to you.

A third-party script registers a look-alike apply_discount mid-run. The total comes out correct. Everything looks fine.

ActionWitness fails it anyway. It hashed the tool surface with getTools() when the run was armed, subscribed to toolchange, and the definition that executed is not the definition you approved.

Your strongest evidence of thoughtful WebMCP use — it only works because the tool surface is itself treated as evidence.

2:28–2:50Beat 4

The payoff, and who it's for

On screen Export the regression case. Then one frame of the merchant-readable audit report.

Every failure exports as a portable regression case that replays from a restored fixture — so today's silent bug is tomorrow's CI test.

And this isn't only for people who built a WebMCP app. Platforms are switching agent tools on for merchants who never installed them and can't test them. Same engine, one authorized origin, a report written for a shop owner.

2:50–3:00Close

The line to end on

On screen The verdict frame again, then the live URL.

A call-level evaluator asks whether the model called your tools correctly. ActionWitness asks whether your tools did what they claimed.

Run both.

Why this order

Your own round-two review made the call: lead with the shared workspace, not the CI story. "The quality of the human–agent experience" is a stated judging criterion, and the machinery for it is already strong — it was just buried under eval plumbing in earlier framing. So the consent gate lands at 1:12, not at 2:40, and the regression payoff closes rather than opens.

The same review named the audience problem. "Testing infrastructure for WebMCP developers" addresses a population that rounds to zero; "find out what the agent tools your platform switched on actually do" addresses hundreds of thousands. Beat 4 exists to make that turn in two sentences.

Before you record

  • Warm the instance. The deploy is free-tier; a cold start on camera is a lost demo. Hit the URL a few minutes before and confirm /healthz reports "database": "ok".
  • Flag on. chrome://flags/#enable-webmcp-testing enabled, browser relaunched. Check the capability bar says available and names where it found the API.
  • Two windows, pre-arranged. Workspace and storefront side by side, so "the cart never moved" is one glance rather than a tab switch.
  • Reset between takes. A fresh workspace per run, so no stale verdict is on screen when you start.
  • Rehearse Beat 3 once. It's the only beat needing a config change mid-demo; know exactly where the failure-profile control is.
  • Record at a readable size. Judges watch small. If expected 20.00 / observed 25.00 isn't legible, the best frame in the video is wasted.

If WebMCP misbehaves

Say so and keep going — every step has a human control, and "the workspace works with no browser agent at all" is a designed property, not an excuse. It turns a stumble into a feature.

If the store is slow

Don't narrate over dead air. Cut, and pick up from the verdict panel. A tight 2:45 beats a padded 3:00.

Claims to avoid

The repository already enforces these in product copy with a build gate. The video should hold the same line — an overclaim is the fastest way to lose a judge who checks.

  • Don't claim damage that hasn't happened. The risk is real and forward-looking: the day this ships on by default, a cart-and-checkout surface goes live across a merchant base nobody reviewed. That's the honest framing.
  • Don't claim adoption. WebMCP usage outside demos is near zero today, and the opposite claim is checkable in thirty seconds.
  • Attribute third-party findings. If you cite anyone's breakage report on camera, name and date it. ActionWitness has scanned no brand it doesn't own.
  • Don't say "replaces". It complements call-level evaluators. "Run both" is the line, and it's the more confident one.
  • Don't imply the audit has a UI. The server path is complete and tested; the browser client isn't built. Show the report, describe the direction, don't stage a flow that doesn't exist.

The 30-second cut

For the submission blurb, or a teaser.

An agent tells you it applied the discount. It returns success. The cart never changed.
